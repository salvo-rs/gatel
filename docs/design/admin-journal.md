# Admin 持久化协议：检查点运行模式已接通，WAL 与幂等协议待完成

默认 HTTP 写入 200 只表示内存应用；显式 `run --checkpoint-journal DIR --checkpoint-instance ID`
启用 checkpoint-only 模式，写入成功还要求保存完成。另提供 journal-compact 离线压缩导出；尚无 WAL、幂等回执或在线轮转；具体边界见 [CLI](../CLI.md)。
带 `admin-api` feature 的构建已有离线 `journal-inspect` 诊断命令，见 [CLI](../CLI.md)。
它只打开已有锁/日志，验证实例与检查点后输出脱敏状态；不初始化、不修复、不应用。
检查句柄拒绝追加、截尾和保存检查点，拒绝误写后仍可继续读取。文件读取可能更新访问时间，
Windows 的已有锁文件需读写权限以取得独占锁；目录内容不作修改。该命令的成功退出不是服务就绪证明。
日志存储与实例绑定已用于检查点模式；意图/结果追加尚未接入生产请求的 WAL。
磁盘格式未作为稳定接口发布。

完整来源的版本化意图载荷已有独立的内部编解码与边界测试，见
[WAL 意图载荷](wal-intent.md)。它尚未接入日志追加、请求去重或恢复，不改变下列生产能力边界。

## 已实现的记录格式

基础 frame 保存 UTF-8 载荷；事务层在其中编码完整 admin KDL 意图或关联意图的结果记录，
不保存 token、活动 Runtime 或其他来源配置树。
顺序号是日志顺序，不是 BootId/generation/SourceRev，不能相互替代。

| 字段 | 字节 |
|---|---:|
| 格式标识 `GATELJ01` | 8 |
| little-endian 非零顺序号 | 8 |
| little-endian 正文字节数 | 4 |
| 正文校验值 | 32 |
| 前 52 字节的头部校验值 | 32 |
| UTF-8 载荷 | 0～1 MiB + 32 字节 |

校验使用现有 Hasher 的独立格式域。先校验完整头部再相信长度；正文长度损坏不能被当作
正常短尾吞掉。校验值是完整性检查，不是 MAC/签名，不阻止拥有文件写权限的人重新伪造记录。
32 字节额外空间供事务信封使用，KDL 原文仍限 1 MiB。编码不解析 KDL；最终宿主必须
在正确的事务边界写结果记录，不能把类型正确的记录当作实际发布已经发生的证明。

恢复扫描输入不超过 16 MiB，返回最新完整原文、最后顺序号、完整前缀字节数和短尾标记，
不自动修改文件。返回原文借用输入，Debug 只包含长度，不打印正文。
初始序号基线由调用者显式传入（全新日志为零），不根据第一条记录猜测；将来 checkpoint
必须独立验证基线及其对应状态。禁止跳号、重复、倒退和溢出。

基础帧读取的 `None` 表示没有完整记录，`Some("")` 表示空载荷；事务层的空配置贡献使用
带 `I` 信封的空正文表达，而非空帧载荷。未知 magic、完整头部/正文
校验失败、非法 UTF-8 或序号错误会使整个扫描失败，不返回看似可用的部分恢复结果。
只有结构仍可能合法的末尾短记录可报告为 incomplete tail；这不能区分“从未承诺的部分追加”
和“曾承诺的数据后来被截断”，后者仍依赖磁盘/备份/回执协议。

### 已实现的意图与结果协议

`Journal` 是基础 `Store` 的类型化入口，在同一独占锁下回放所有完整记录，而非只看末条载荷。
打开时必须显式传入稳定实例身份（1～256 个无空白可打印 ASCII 字节），不使用每次启动变化的
BootId、bearer token 或猜测的当前目录。第 1 条 frame 为 `GATEL-INSTANCE1\n<身份指纹>`，
指纹使用独立 `gatel.admin-journal.instance.v1` 域。空日志先写入并同步绑定，第一条意图从序号 2 开始。
实例身份非法时在文件操作前拒绝；身份不匹配在回放事务前拒绝；绑定短尾、重复绑定、未知版本、
没有绑定的旧实验日志均拒绝，不截断、不迁移、不让当前调用者认领。完整绑定后的合法事务短尾
仍可走显式修复流程。没有完整绑定的故障恢复需要另行人工策略，当前未提供 CLI 修复入口。

身份不以原文写入日志，但指纹不是秘密或认证凭证；低熵身份仍可猜测。两个部署使用相同身份、
拥有写权限的人改写整个日志、日志彻底丢失/清空均不在此绑定防护内。宿主后续仍须定义实例身份
的配置来源、日志位置和全来源配置的归属；该接口不会自动从目录推导身份，也不绑定特定机器。

信封版本为 `GATEL-TX1`，记录如下（`\n` 表示一个换行）：

| 载荷 | 含义 |
|---|---|
| `GATEL-TX1 I\n<KDL 原文>` | 新意图，以本条 frame 顺序号为身份，正文可为空 |
| `GATEL-TX1 A\n<意图顺序号>` | 宿主明确确认该意图已应用 |
| `GATEL-TX1 R\n<意图顺序号>` | 宿主明确确认该意图被拒绝 |

结果引用必须是规范十进制，并恰好引用当前唯一未决意图；没有意图的结果、重复/矛盾结果、
越过未决意图的新意图、未知版本和旧的裸 KDL 载荷均报错。旧实验日志不自动迁移或覆盖。
发生语义错误时整个打开失败，即使 frame 的校验值有效。回放状态是局部暂存，失败不暴露部分状态。

状态分别保存最新意图、其可选结果、最后明确确认应用的 admin 贡献。拒绝不会覆盖最后确认贡献；
完整意图后没有完整结果就是“未知”，不能因重启、调用者取消或短尾修复推断为拒绝或成功。
未知意图必须先由未来宿主恢复流程核实并写入结果，才能接受下一条意图。空原文是明确的空贡献，
与从未确认任何贡献不同。Debug 只打印原文长度，不打印配置内容。

写入先在候选状态校验转移，只有底层 append + sync 成功才替换可见状态。非法操作不写盘、
不污染写者；I/O 失败仍遵循 Store 的 poisoned/重新打开规则。这不是幂等 API：重复结果当前报错，
尚未提供客户端请求键、历史查询和可查询幂等回执。
新意图必须同时满足自身和一条最大结果记录的容量需求，避免达到 16 MiB 逻辑上限后无空间
落下结果；不预分配磁盘块，不保证真实磁盘空间或 sync 成功。现有检查点保存本身不释放日志空间。
完整覆盖日志的检查点可通过 journal-compact 离线导出到新目录以回收容量；未覆盖或未决状态必须先协调，在线轮转尚未实现。

容量拒绝发生在追加之前，不留下新的未决意图，也不污染写者；仍可检查和保存检查点。
保存检查点、关闭再重开均不会增加剩余容量。不要单独删除或截断 `intent.log` 来恢复写入：
检查点绑定其日志前缀，手工改动会使恢复校验失败。当前没有自动或受支持的原地轮转命令。

**最后确认的 admin 贡献不是完整 Runtime 的 LKG。** 文件 watcher 可与保留的 admin 意图组合后
成功发布，即使那份 admin 意图先前被拒绝；未来集成必须记录所有来源触发的有效发布组合，不能
仅在 Admin PUT 成功时写 `A`。源文件内容、插件/资源身份、启动环境、activation 和发布顺序仍须
由完整 checkpoint/宿主事务协议处理。当前 `finish(Applied)` 接受可信宿主判断，不自行验证运行状态。

## 接入前必须完成的事务决策与验收

### 已实现的磁盘基础

`Store::open` 要求已有私有目录，打开持续保留的 `writer.lock` 并取得 OS 独占锁，
然后打开 `intent.log`；没有取得锁时不读取/追加日志。关闭句柄释放锁，不删除锁文件。
锁由取得成功后立即建立的 WriterLock 守卫拥有；正常析构（包括打开后续校验失败）
显式 unlock，而非只依赖 File close。Linux flock 的 dup/fork 副本共享 open file description，
最后副本关闭前可能持续持锁；CLOEXEC 不能消除 fork 到 exec 的窗口。守卫记录所有者 PID，
避免 fork 子进程析构时误解父进程锁。unlock 错误在析构中不能返回，仍依赖随后 close/OS
释放兜底；进程 kill 不执行析构，原有 kill/reopen 测试仍适用。不支持在 fork 子进程继续
使用父进程的 Store。参见 [Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html)。
拒绝可见的最终目录/文件符号链接及非普通文件，Unix 检查目录和打开句柄的私有权限；
Windows ACL 仍由操作者负责。这是合作式本地进程协调，不是恶意父目录替换防护。

读取前检查文件大小，并用 MAX_LOG + 1 有界读取再校验。新建文件同步后，Unix 同步父目录；
Windows 没有等价的目录同步承诺，也不保证所有文件系统/硬件都提供断电持久性。
短尾可以打开查看完整前缀，但不允许继续追加，不自动截断或修复。损坏记录打开失败。
内部显式 `discard_incomplete_tail` 可丢弃打开时观察到的未完成后缀：在持续持锁下重新
有界读取整个日志，校验完整内容指纹、记录前缀及恢复状态与打开时一致，才执行截断并同步。
同长度的前缀或尾部改写也会被拒绝。检查或截断/同步失败会污染句柄，必须关闭重新检查；
同步失败不代表截断未发生。成功返回丢弃字节数，保留原顺序号，随后可以继续追加。
无短尾时返回零，不执行修复检查；这不是通用文件完整性审计。完整损坏记录不能借此跳过。
此方法尚无 CLI/HTTP 入口，不授权自动删除数据，也无法防御忽略写锁的恶意本地写者。
当前磁盘层只支持从零开始的完整日志，尚不支持非零 checkpoint 基线和在线轮转。
离线压缩保留双快照/原发布身份，重绑定到新目录中从序号 1 开始的实例绑定日志；不修改原目录或自动切换部署。

append 成功须经过 write_all + sync_all，之后才推进内存顺序号。进入可能改变磁盘的阶段后
任何错误都会使该句柄停止接受追加，要求关闭、重新检查结果；完整记录可能已经存在，
不能把返回 Err 理解为磁盘必然没有改变。纯输入/容量校验失败不污染句柄。
追加前检查当前文件长度，不能据此检测同长度的未授权改写；所有写者必须遵守独占协议。

测试覆盖同进程独立打开的排他性、重新打开、部分追加及模拟同步错误、短尾不截断、
损坏/超限/非普通文件、Unix 权限与符号链接。
另有真实子进程故障测试：子进程持锁并同步完整记录后停留，父进程确认不能取得写锁，
强制 kill 并 wait 后重新打开，验证 OS 释放锁、完整记录保留且可继续追加；另一轮预先
同步第二条记录的部分字节，kill 后仍只恢复第一条并拒绝越过短尾追加，不自动截断。
Linux 还检查 SIGKILL 状态。该测试刻意固定部分字节以验证分类，不模拟真实 torn sector、
电源故障、未刷盘数据丢失或 HTTP 发布/回执窗口，不能代表全部崩溃恢复已完成。
类型化日志另有三轮子进程 kill：已同步应用结果、拒绝结果或只有未决意图。重启时先验证外来
实例不能打开，再验证正确身份恢复最后确认贡献和最新意图；未知结果仍阻止新意图。此测试的
Applied 是测试宿主直接写入的结果，不代表真实 Runtime 的 publication/activation 已验收。
磁盘 I/O 是同步接口，宿主以后必须放入有界 blocking 执行链，不在异步 reactor 或 generation 锁内调用。

### 已实现的宿主事务边界

`CheckpointSession` 接管尚未使用的 App 和单个检查点写者。启动前拒绝 reload 和 Admin
构造；新目录从文件启动，已有检查点先恢复双快照并确认激活，再开放同写者的来源更新。
准备失败时保留恢复输入供重试，成功后拒绝重复 startup。它统一协调现有事务入口，
不引入另一套发布流程；只读服务/状态访问可取得 App，可信宿主不得借此绕过策略写入。
会话集成测试串联真实 Admin PUT、文件 NoOp 观察更新、关闭重开、当前文件损坏时恢复
已保存服务，以及修复文件后沿用恢复修订继续 reload。显式检查点 CLI 使用此会话。

`watch::reload_checkpoint_until` 将会话接入现有 watcher 循环，复用目录发现、通知合并与
5 秒兜底轮询。纯 CAS 冲突没有开始写入，可继续等待后续观察；其他提交错误记录
`checkpoint_reload_failed` 并返回宿主，不自动重试或降级为内存写入。函数不擅自停止
业务服务，调用它的运行宿主负责终止或协调恢复。真实文件测试覆盖成功保存、磁盘故障后
返回 PersistenceUnknown、保留旧服务，以及路径修复后仍拒绝跳过写者锁存。

`AdminApi::with_checkpoint` 在宿主构造 HTTP 适配器时绑定检查点来源写者，沿用普通
Admin 的认证、请求容量、字节限制与 If-Match 校验。真实 TCP 回归验证保存完成才返回
200，旧版本返回 412；发布并激活后遭遇真实文件保存失败则返回 503，正文明确可能已应用，
不附 ETag 或 Retry-After。修复磁盘路径后继续请求仍被锁存拒绝，重开检查点保留最后一次
成功 200 对应的完整双快照。CLI 通过会话把它与文件前端纳入同一检查点策略，不提供 WAL 或幂等键。

HTTP 生命周期回归还在发布后用检查点锁阻塞保存，待激活完成后断开真实客户端并关闭
AdminServer：此时磁盘仍为旧检查点，应用的提交执行锁仍被占用。释放阻塞、等待 App
提交排空后，重开校验包含新来源的完整双快照。该路径证明请求/连接任务退出不取消已接收
的应用提交；客户端断连后仍无法知道最终结果，不等同于已提供幂等查询或崩溃恢复保证。

`App::reload_frontend_checkpoint_if` 为文件前端提供相同的检查点收尾。它在文件读取、
修订缓存更新之前检查 Version 与写者就绪状态，再复用普通 reload 的 `attempt`，
合并其他来源的最新意图并处理外部资源刷新。调用者必须使用执行时仍有效的 Version；
冲突不擅自重试。真实文件回归验证 stale 请求未推进文件缓存、NoOp 的新文件修订被保存、
文件更新保留被拒绝的 Admin 意图，以及写者故障优先于后续文件解析。
显式检查点模式的 watcher 使用该入口；默认模式保持内存语义。

`App::checkpoint_source_writer` 在签发句柄时绑定来源与 CheckpointWriter，调用方仍使用
`reload_if` / `reload_kdl_if`，不能在每次请求中选择其他来源或更换持久化策略。
它沿用普通来源写者的 CAS、修订分配、输入限额和来源合并逻辑；预检位于 CAS 之后、
解析与观察之前，激活后的保存则与完整 Snapshot 入口共用 `finish_checkpoint`。
句柄只弱引用 App，但持有检查点写者，保留句柄会继续持有其磁盘锁。

来源级回归覆盖 Admin 更新保留文件贡献、冲突不修改磁盘、语法错误不生成新来源修订、
编译拒绝后分别保存旧服务与新观察快照，以及失败锁存后拒绝后续请求；重开比较完整
快照编码，并用真实 HTTP 验证原服务仍在。语法错误诊断不属于检查点来源快照，不承诺
重启后恢复该诊断。此入口没有开启全局持久化模式：宿主仍须统一路由所有参与来源，
恢复已存在的检查点，并完成生产策略接线，不能混用内存写者后宣称所有更新均已落盘。

来源句柄还通过确定性取消/关闭回归：在发布后、激活前取消等待者，用独立阻塞线程
持有检查点锁，待激活完成后启动真实 shutdown。旧检查点在释放锁前保持不变，
关闭等待尚未保存的事务，释放后完成保存和连接关闭；重新打开校验双快照的完整编码。
该测试验证进程内任务所有权，不是进程崩溃或断电恢复的证据。

宿主现在可使用内部 `CheckpointWriter`，只取得打开/保存完整检查点的能力，不暴露
Journal 的原始追加/结果确认/截尾。打开时验证实例、完整日志和检查点，只接受绑定后
未初始化状态或日志完全被检查点覆盖的状态；返回已有双快照，要求宿主先恢复后覆盖。
未决、检查点后已应用或被拒绝的意图均要求显式协调，不能以保存新检查点跳过。
真实 App 的 blocking completion 已有写盘/重开集成测试，显式检查点 CLI 已启用；
底层写者本身不证明 capture 已激活或绑定请求，仍由会话与宿主事务保证。
该宿主能力在任意 save 失败前先进入失败状态，只有完整成功才恢复可写；编码/验证错误
也不允许同一句柄继续覆盖，因为宿主内存可能已先行发布。这比底层 Store 的 I/O poisoned
规则更严格。`ensure_ready` 供串行执行门内、发布前预检，不是预留成功写盘的保证。
失败句柄保持原独占锁，直到宿主主动关闭；重开返回磁盘快照供核查，不证明内存与磁盘已一致，
不得通过自动重开继续写入来绕过协调。
一个打开的 CheckpointWriter 能力只绑定一个 App BootId：在宿主发布前 bind，save 再检查
capture 的 BootId。两个 App 共享同一 Arc/Mutex 不能绕过各自 execution gate 的隔离；
外来生命周期的 bind/save 在修改前拒绝，且不污染原所有者。绑定只存在于内存，重开会清除；
它不替代持久化 instance 标识，也不是网络身份认证。
重开已有检查点还会进入 recovery-pending，ensure_ready/bind/save 全部拒绝。宿主在
恢复后调用 confirm_recovery：完整 serving 和 observed snapshot-codec 字节分别按独立域
取指纹，比对成功且 capture 未 sealed、有 committed 后才清除 pending 并绑定新 BootId。
这包括修订、内容指纹、节点和来源信息，不只是版本号或归一化 plan；确认不写盘，错误
输入不消除 pending，正确输入可以随后重试。确认只允许一次，不能借它重新绑定写者。
该检查确认来源身份，不验证监听器健康、外部资源等价性或 activation；宿主仍须在 owned
execution 下完成这些检查。新建绑定但无检查点时不需要恢复确认。
内部 `App::recover_checkpoint_if` 已把来源预检、恢复、activation 与确认放入同一个
owned execution；磁盘不在确认阶段改写。预检先检查冷启动条件及完整 Version，再预留新 BootId，另一个 App 即使有相同
来源也不能同时恢复或抢走确认。普通只读 bootstrap 与此入口共用 recover_snapshot_if
资源准备/发布实现。等待者取消不取消确认；输入/恢复失败与“可能已发布但确认失败”
使用不同错误类型。该入口由检查点会话用于可写 CLI 恢复，随后按同一会话策略继续写盘。
内部 `App::reload_checkpoint_if` 将完整 Snapshot 的 Version CAS、写者预检、prepare/
publication、activation、blocking 检查点保存串入同一 owned execution。冲突不写盘，
失败写者在观察/发布前被拒绝；保存失败返回 PersistenceUnknown。没有已激活服务版本
可保存时，已保留的来源意图仍要求写者进入协调状态，不将首次被拒绝配置伪装成已经有可恢复的检查点。
例外是版本未变、没有服务状态且没有任何来源意图的初始拒绝（例如缺失文件、语法错误）：
返回 Rejected，保留内存诊断，不创建检查点、不锁死写者；修正输入后可使用相同写者重试。
回归先在旧实现复现失败，再覆盖 inline 语法错误、文件缺失/语法错误及修正后的真实 HTTP 服务。
Stale 只有在完整 Version 未变时才跳过保存，避免关闭竞争后已观察的新意图被遗漏。
该完整来源入口供可信宿主使用；检查点 CLI 的 watcher/Admin 使用各自来源入口，共享相同
保存收尾。调用者须先恢复已有检查点并统一所有来源策略。检查点成功不提供意图预写日志、
请求幂等键或可查询回执，崩溃在保存之前仍可能恢复上一个检查点。

宿主已有内部 `reload_task_finishing` 收尾入口：普通路径使用原样返回结果的空收尾；
可信持久化适配器可在 work 的 `Result` 产生并完成所需 activation 后执行收尾。
收尾仍由 owned job 持有 reload execution 锁及准入名额，取消等待者不取消收尾，
后续 watcher/Admin 事务不得提前进入。work 返回错误也交给收尾判断，但准入失败或
排队后发现 sealed 时两段回调都不运行。收尾错误直接返回，不伪装成未应用或 CAS 冲突。
内部 `reload_task_persisting` 已为同步持久化回调提供专用 blocking 入口：每个 App 的
执行锁只允许一项收尾，沿用已接收事务的准入，不经过可能已被 shutdown 关闭的
configuration_work。回调结束前宿主不会释放顺序锁或完成 shutdown；取消请求等待者
不取消回调。回调没有持有 generation/lifecycle 锁，可以捕获配置或写盘。panic 继续
传播并释放名额，不转换成成功；此时仍需由后续恢复核实磁盘结果。
这不是写盘实现；未来适配器仍须处理 activation 返回但服务已经关闭的情形。不得把进入收尾
等同于服务健康或 durable ACK；panic/进程终止仍依赖日志恢复协议。

检查点输入基础：`Committed::source_snapshot()` 现提供与该 generation 的 runtime/revs 同时
固定的完整编译来源快照。树在 generation 写锁外复制，旧连接持有旧 generation 时仍保留其
原始快照；后续失败观察、prepare 失败或 stale 候选不会覆盖它。NoOp 不建立新 generation，
因此也不替换这份构建来源，不能拿它当最新成功观察或当前写前置版本。
该接口面向可信宿主，配置可能含秘密，Committed 的 Debug 不输出它。保存副本增加了每个
被固定 generation 的内存占用；没有零拷贝、密钥擦除或性能无回退承诺。它是 lowered Node
树，不是原始文件备份，也不包含外部资源和 activation 状态。来源树已提供独立有界
[编解码器](snapshot-codec.md)及[检查点封装](checkpoint-envelope.md)，全来源原子取样和
显式只读启动和 checkpoint-only 可写运行均已接入。默认内存模式的 HTTP 200 语义不变，
只有显式检查点模式的写入 200 才包含检查点保存完成；不代表已有幂等回执或 WAL。

### 仍需完成的生产集成

多来源历史校验现由模型层 `Snapshot::validate_successor` 统一提供，检查点与冷恢复共用：
来源不可省略、修订非零且不倒退、同修订完整节点身份必须一致；允许新修订 tombstone 和
语义无效的最新意图。校验直接比较节点（含来源位置、顺序、浮点位），不再为同修订历史
重复编码或克隆整棵树。它不提供来源授权、大小预算、CAS、编译或持久化保证。

完整 WAL 仍不能直接复用当前 GATEL-TX1 的 Admin 文本意图：该负载上限约 1 MiB，而
完整来源快照编码可达 16 MiB，且文本不包含其他来源的修订/贡献。后续必须显式定义完整
来源意图、前置版本、请求身份及决定回执的版本化记录与容量策略，再接入宿主执行链；
不能通过静默放大旧记录或截去其他来源来宣称完成。

以下为完整 WAL 协议的验收要求。位置/身份 CLI、检查点启动恢复、同会话 watcher/Admin
与保存失败语义已经实现；仍须把预写意图/结果、幂等回执、轮转和全面崩溃测试补入该链路。

1. 将上述意图/结果状态接入全来源发布回执与 LKG checkpoint。仅保存最新意图不足以在最后一次
   配置被拒绝后恢复先前服务状态；不能把本 codec 的最新原文直接称为 last-known-good。
2. 将已实现的实例绑定和独占存储接入宿主配置，确定日志位置和实例身份来源；验证读取句柄、文件类型、
   大小和权限。先有界读取再调用 codec；codec 的长度检查不能撤销调用方已经分配的内存。
3. 为写盘、sync、配置观察、prepare、发布、activation 和 HTTP 回执建立明确顺序。
   在同一有界执行链里协调文件 watcher 与 Admin，不能依赖两次独立 Version 查询排除竞态，
   不能持有 generation 写锁做磁盘 I/O。
4. 定义每个失败窗口的客户端语义：提交失败、结果未知、可重试与不可重试。连接断开后已接收
   任务仍由 App 拥有；响应丢失不能触发不带幂等键的盲重试。只有相关持久化条件已满足才可
   返回持久化成功，内存提交后写盘失败不能伪装成完全未应用。
5. 启动时先恢复并校验 checkpoint/日志/文件来源组合，再开放业务和管理监听。损坏需要明确
   失败或人工恢复策略；不能静默回退旧文件。恢复后 BootId 必须更新，旧 ETag 不跨重启有效。
6. 将已实现的显式短尾处置接入恢复策略和操作者确认；单有 `valid_bytes` 不授权删除。
   checkpoint/压缩需临时文件、同步与替换协议；当前 16 MiB 上限不是已完成的日志轮转方案。
7. 对每个写盘/提交边界做崩溃注入与重启验收，覆盖空配置、拒绝意图、外部文件变化、多个
   重启竞争、同步失败、满盘、损坏与回执丢失。字节截断单测不等同于真实进程崩溃测试。
