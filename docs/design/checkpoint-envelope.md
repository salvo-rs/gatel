# 检查点封装与内部磁盘存储

`admin_checkpoint.rs` 将已发布来源、最新完整观察来源与实例、注册表和日志前缀关联。
Journal 已提供文件读写与替换，显式 checkpoint-only run 已接通启动恢复和运行期保存。
检查点模式的写入 200 包含保存完成，但尚无 WAL、幂等请求回执或日志压缩。

格式 `GATELC02` 的头部为 8 字节 magic + 32 字节正文校验；正文为固定 176 字节元数据，
然后是已发布快照编码长度（u64 little-endian）、已发布 `GATELS01` 编码、最新观察 `GATELS01`
编码。元数据按序保存：实例指纹、Registry build_hash、plan_hash、
历史发布身份指纹（各 32 字节），日志顺序号及前缀字节长度（各 u64 little-endian），
日志前缀指纹（32 字节）。每份快照独立限制为 16 MiB，总长度上限为 32 MiB 加 224 字节；
先验证总长度和正文校验，再有界分割两份编码，不按声明长度预分配无界对象。
正文校验使用 v2 域，各身份域保持隔离；校验不是签名、MAC 或加密。
旧实验 `GATELC01` 明确拒绝，不能自动补成最新意图或静默覆盖，需单独迁移策略。

创建时要求日志包含正确实例绑定、所有完整记录符合事务状态机、没有短尾或未决意图。
写入入口只接受 `ConfigurationCapture`，从其 pinned Committed 取得服务来源，使用传入 Registry
重编译并确认 plan_hash 匹配后编码；没有已发布 generation 的 capture 不能创建此检查点。
最新完整意图单独编码，不要求 normalize 通过，因此语义拒绝、prepare 失败、NoOp 与空贡献可保留。
历史发布身份由完整 BootId + generation 的独立域 hash 表达，不恢复旧 BootId 或旧 ETag。

读取时依次校验总长度、版本/校验值、实例和 Registry，再回放整个传入日志。检查点指定的前缀
必须存在，字节指纹和顺序号完全匹配，并结束在无短尾、无未决意图的完整边界。前缀后面的
完整记录损坏或非法事务也会拒绝，不能借旧检查点隐瞒；后续合法未决意图/短尾可以存在，
但仍需要另外的恢复处理，解码成功不是允许忽略它们。

随后解码两份来源，只重编译服务来源并确认 plan_hash。两边修订都必须非零；每个服务来源须在
观察来源中存在，修订不得倒退；相同修订号的来源必须完整编码一致（含原始指纹、树和来源位置）。
不允许用“缺失”表示删除，须保留较新空贡献。观察来源可以包含新来源或非法配置，不能强制用服务
来源覆盖。错误仅返回静态说明，Debug 只额外报告观察来源数量，不显示快照正文。
注册表 build_hash 只能反映已纳入其算法的版本/指令信息，不等同于整个二进制、操作系统、
证书/密钥、环境变量或其他外部资源身份；宿主后续必须定义完整兼容策略并验证资源。

特别注意：这些校验验证的是内容关联和编译一致性，不证明输入日志和 Committed 在实际运行中
属于同一个原子时刻。编码器无 Store/App 访问权，可信宿主仍须在全来源写者协调下取得匹配输入，
验证 publication/activation 边界，不能在两个独立查询之间任由 watcher 或 Admin 写入。
创建时无未决意图的限制也不能替代该协调。快照包含 lowered Node 而不是原始文件备份。

`GenerationStore::capture_configuration()` 现提供单次读锁下的原子取样：固定完整写版本、
已发布 `Committed`、全部已准入来源的 Arc，以及 sealed 状态；释放锁后再复制来源树。
`ConfigurationCapture` 字段私有，不允许调用者拼接两次读取的结果；只读访问器分别提供
发布来源和最新观察来源。NoOp、语义拒绝、prepare 失败以及正在 prepare 的候选都可能使两者
不同，不能用其中一份覆盖另一份。Debug 不显示来源名称、正文或 runtime。

捕获不会等待正在运行的候选，也不冻结后续写者。宿主仍须在 owned execution 区间内取样，
再与日志关联，确认 activation，并将两份来源分别持久化。当前 GATELC02 已使用此接口保存两份来源，
显式 checkpoint-only 模式的运行期 reload 已采用该保存策略；只读 bootstrap 与默认内存模式不写检查点。保留 capture 也会
保留旧 runtime 资源和包含秘密的来源树，不承诺内存零开销或密钥安全擦除。

计划层现提供 `restore_intent_if(expected, observed)`：宿主先用正常事务准备/发布服务快照，
再在开放配置写者前恢复最新完整意图。它只做准入和历史校验，不 normalize、prepare、发布或
activation，因此不会把被拒绝的配置作为新 runtime。整个 Version（含新 BootId）在锁外复制/
校验前后均核对；修订不得遗漏/倒退/为零，相同修订的内容指纹和完整树须一致，来源白名单、
数量上限和 sealed 状态继续生效。混合有效/无效来源的失败不部分推进 head。

恢复保留当前 runtime、generation、新 BootId 和已有故障状态，仅原子替换观察来源与 head，
推进的修订使更旧的准备候选失效；旧来源树在锁外释放。它不重建历史故障诊断、不证明最新意图
有效、不等待同版本候选结束，也不授予 activation 或 durable receipt。此入口是可信宿主恢复
能力，不向 Admin HTTP 暴露；生产启动仍需编排检查点/日志结果、资源验证、激活和监听顺序。
磁盘往返测试已验证新 GenerationStore 可分别恢复有效服务来源和无效观察来源，后者不更换
服务 Arc，且重启 BootId 与旧 capture 不同。实际进程只读启动的接入和验证范围见下文 bootstrap 段落。

恢复提交窗口另有确定性测试：在锁外校验完成后、获取最终写锁之前插入普通发布、同修订资源
refresh 或 seal。恢复分别返回 Conflict/Sealed，并保持赢家来源与 runtime；同修订 refresh
证明最终 CAS 比较 generation 而不只是来源修订。该私有接缝不暴露给宿主，生产入口为空回调。

冷启动计划层入口 `recover_if(expected, serving, observed, registry, prepare)` 已将上述两步
串成一个恢复事务：仅允许尚未发布 generation 的 store；先对两份来源做白名单/容量/非零修订/
完整历史校验，失败时不观察、不准备。随后通过完整 Version CAS 准入观察来源，把它作为候选
版本屏障，使用服务来源执行现有 normalize/compile/prepare/commit 流程。提交的 Committed
保存服务来源，head/intent 保留最新观察来源，避免先服务后恢复意图的窗口。

prepare 失败不发布 runtime，但保留已经观察的意图和故障状态，可使用新 Version 重试；并发
发布或 seal 仍会阻止迟到提交。已运行宿主明确返回 AlreadyPublished，不是 live rollback API。
入口不会验证磁盘日志和 activation，宿主必须仍在开放监听/配置写者之前编排这些步骤。
五项新测试覆盖双快照、非法来源不触发 prepare、prepare 失败重试、跨 BootId/已发布/seal
拒绝，以及 prepare 内被发布或关闭抢先；磁盘往返测试也使用该入口重建两份状态。

App 内部已有 `recover_configuration` 高层入口，经过普通 reload 的有界任务准入、owned
execution 互斥、有界 blocking 资源准备与 activation；等待者取消不取消已接收任务。
普通 reload 和恢复共用 `prepare_runtime`，复用相同的 listener/state/TLS/插件退休资源。
真实 HTTP 测试验证有效服务配置响应、无效最新意图独立保留，以及 activation 暂停时取消
等待者后仍完成启动；非法双快照不发布、不激活。已发布宿主不能再次走恢复入口。

`run` 已通过可选 `--bootstrap-journal` / `--bootstrap-instance` 接入只读引导：在管理监听创建前
校验磁盘状态，仅接受 CheckpointCurrent，将双快照移动到 App 的 owned 恢复任务，避免在异步
reactor 上深复制配置。日志检查/解码在创建 async runtime 前执行；独占日志锁保留到关闭。
未覆盖的后续记录一律拒绝，包括明确拒绝的意图，不推测如何合并或自动回退磁盘配置。
后续 reload 仍不持久化，重复引导会再次加载旧检查点；这是显式引导工具，不是生产 durable
mode。配置细则见 [CLI](../CLI.md)。已关闭/满队列仍沿用 reload 的 Stale 结果，不能当成恢复成功。

文件观察现使用准入状态作为恢复基线：一次 reload 先捕获完整 Version/意图，然后单文件或
多根文件按来源选择该意图与本地读取缓存中修订较新者（相同时以已准入状态为准）。恢复后的
revision 不再从 1 开始；同内容沿用修订，改动从恢复值递增。保留较新的本地缓存，避免某次
读取后未准入的观察修订被回退。多根文件仍全部读取成功后才替换缓存，失败不部分推进。
这里只观察配置指定的文件来源，不把 Admin 贡献当作文件；最终发布仍检查读取前的完整 Version。
这不自动决定重启期间磁盘改动应何时生效，启动协调器仍须确定先恢复服务还是先验证新文件的策略。

只读引导还有真实运行子进程测试：直接执行 run 启动路径，缺失根 KDL 时从检查点对真实 HTTP
请求响应；连续请求期间竞争日志打开失败。父进程强制 kill 并 wait 后重新取得日志锁，验证
检查点可加载、日志/检查点字节完全不变；Unix 验证 SIGKILL。子进程使用测试 harness 执行
实际 run 函数，不是模拟 App；此用例不包含优雅信号关闭、运行期持久化、OS 崩溃或断电。

宿主高层 reload 已增加 owned execution 互斥，覆盖工作闭包、activation 和收尾；内部
reload_checkpoint_if 已将保存放入此区间，recover_checkpoint_if 也在同一区间完成恢复确认。
显式检查点会话将它们用于 watcher/Admin/CLI，不能返回 Outcome 后另行读日志/写盘。App 的可写
GenerationStore 及低层 attempt/attempt_snapshot_if、attempt_async、activate 现已限制在事务模块
内部；Admin/watcher/CLI 仅持状态副本，高层写入经过执行互斥。内部宿主代码和测试仍能直接
执行阶段，因此是模块边界约束，不是对可信宿主代码的安全沙箱，也不是持久化已经接通的证明。

测试覆盖独立新 BootId 重编译、实例/注册表/同序号不同历史拒绝、每个截断和单字节改写、
正确校验下的错误前缀/顺序号/来源树，以及旧前缀后未决、短尾和完整损坏记录。测试使用空的
PublishRuntime，属于封装层验证；上文另列真实 App/HTTP 集成验证，二者都不是断电或 HTTP 持久化回执故障验收。

## 内部磁盘读写

保存时仍校验完整日志、待保存封装和现有检查点的类型/权限/尺寸/内容。若现有已校验封装
与候选字节完全一致，则跳过临时文件写入、sync 与 rename，减少 watcher 稳态轮询的重复
替换；不是按 plan hash 或 generation 单字段跳过。来源观察修订、发布生命周期或日志前缀
变化仍会导致保存，损坏/不安全的现有文件仍报错。这只减少写入，不免除编码、读取或校验开销。

### 恢复检查与后续处置

`Journal::inspect_recovery` 在加载并验证检查点后，只分类、不应用、不修改文件。返回检查点、
最新意图、最后明确应用的 admin 意图、最新结果、日志顺序和短尾标记，Debug 不输出配置正文。

| 分类 | 含义与宿主后续责任 |
|---|---|
| Uninitialized | 只有绑定、没有检查点；仍需取得初始文件来源，不能直接开放服务 |
| CheckpointCurrent | 检查点覆盖全部完整日志；仍需来源准入、环境/资源验证和正常准备/激活 |
| CheckpointWithRejectedIntent | 后续没有成功应用，但有拒绝意图；服务快照与拒绝意图必须分开保留 |
| IncompleteTail | 先走显式短尾处置，再检查；不能顺便推断未决结果 |
| UnknownOutcome | 完整意图缺少结果，必须核实，不能盲目重放或当作拒绝 |
| MissingCheckpoint | 已有完整事务但无检查点，不能冒充全新初始化 |
| AppliedAfterCheckpoint | 检查点之后有成功应用，即使最后一次被拒绝，也不能静默采用过期检查点 |

后四项属于 Reconcile 分类。短尾与未知结果同时出现时优先报告短尾，但返回的 latest/decision
仍保留未决事实；显式修复尾部后再次检查必须继续报告未知。完整损坏、实例或注册表错配直接
返回错误，不返回上述可用分类。检查点之后的拒绝意图不能自动合并进服务快照，也不能遗忘。

这里的 Current 仅指日志覆盖关系，不证明操作系统、文件来源或 Runtime 状态已经恢复；尤其是
尚未接入日志的文件 watcher 发布仍不能由此判定。整个日志或目录被外部删除/清空也不在此分类
可检测范围内。此接口已接入只读 `journal-inspect`、bootstrap 和可写检查点会话启动，
但成功检查本身不等于资源已准备/激活，不能当作 readiness 或写入回执。

`Journal::save_checkpoint/load_checkpoint` 使用打开时固定的实例身份，委托同一个 Store，
在其持续持有的 `writer.lock` 下操作固定文件 `checkpoint.bin`。存储目录先转绝对路径再检查，
后续当前目录变化不会把写入导向另一个相对位置。父目录仍必须可信，不是恶意目录替换沙箱。

读操作先有界重新检查日志，再验证检查点最终路径及打开句柄为普通文件；Unix 检查私有权限，
Windows ACL 由操作者负责。文件缺失返回 None，不创建检查点；存在时先检查大小再以
MAX_BYTES + 1 有界读取，随后执行完整封装/日志/计划校验。Journal 打开本身尚不自动检查
checkpoint.bin，未来启动恢复入口必须在开放监听前显式加载并处理失败。

写操作先编码候选，并加载验证现有检查点。损坏、超限、外来身份、注册表不兼容或不安全路径
均拒绝替换，不自动迁移。验证成功后，在同目录以 create_new 创建临时文件（Unix 0600），
write_all、sync_all、关闭句柄，再 rename 覆盖目标；Unix 随后同步父目录。Windows 不提供
等价目录同步承诺，不保证任意文件系统、硬件或断电下的持久性。

进入临时文件写入阶段后任何错误都会 poison 同一个日志写者，追加、保存和加载须关闭重开后
重新检查；Err 不能解释为目标没有改变。替换前失败时旧文件保留，替换后错误时新文件可能已经
可见。正常错误展开会尽力清理自己创建的临时文件，成功 rename 后不再按旧临时路径删除；
强制终止可能留下临时文件，打开不自动清理或将其当作检查点。本实现不压缩或截断 intent.log。

所有写者必须遵守锁协议。重新读日志检查顺序、长度、末条原文和短尾状态，但不是对忽略锁者
的持续完整性监控；不能防止恶意进程同长度重写历史再重算校验。写锁也不等于宿主 generation
锁，宿主仍须将实际配置发布与检查点取样协调起来。同步 I/O/编译必须运行于有界 blocking 工作，
不能放在 async reactor 或 generation 写锁内。

磁盘测试覆盖首次写入/替换/重开、日志不改写、无未决意图门槛、五个边界注入失败、临时文件
清理、损坏/超限/非普通文件；Unix 另验权限及符号链接。

另有真实进程 kill 测试：首次写入的临时文件同步后/rename 后、覆盖旧检查点的临时文件同步后/
rename 后/目录同步阶段后，共五轮。父进程先确认子进程仍持独占锁，再 kill + wait（Linux 检查
SIGKILL），重开后验证正式文件为缺失、完整旧版本或完整新版本，日志字节不变。临时文件同步后
终止会留下完整 orphan，恢复不将其当成正式检查点；后续正常保存也不擅自删除该 orphan。
替换前旧检查点引用 journal 序号 1，替换后新检查点引用序号 3，因此同时验证跨记录前缀关联。
这不模拟 OS 崩溃、断电、torn sector、真实满盘或 sync 系统调用失败；Windows 的目录阶段钩子
不代表执行了 Unix 目录同步。生产发布/HTTP 回执窗口仍待集成后验收。

GATELC02 的上述进程 kill 夹具在新旧检查点中分别保留不同的语义拒绝意图；恢复时不仅核对
计划和前缀序号，还比较完整观察快照编码，并确认服务来源可编译、观察来源仍被拒绝。
独立测试另验拒绝后 NoOp 空贡献、磁盘重开双快照、正确校验下的遗漏/倒退/同修订篡改与长度边界。
